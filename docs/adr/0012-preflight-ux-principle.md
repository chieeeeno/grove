# ADR-0012: 事後エラーより事前警告を優先する UX 原則

**日付**: 2026-04-07
**ステータス**: 確定

## 背景

VS Code 起動ボタンの実装方針を検討する中で、「`code` コマンドが見つからない場合の挙動」について議論した。
この議論の中で開発者本人から「ユーザーがボタンを押した後にエラーダイアログが出るのは UX が悪い。事前に分かっている問題は事前に伝えてほしい」という強い意見が出た。

これは VS Code ボタンに限った話ではなく、Grove 全体の UX 設計に通底する原則として残しておく価値がある。

## 検討した選択肢

ある操作に対して、前提条件が満たされていない場合の通知方法:

- **A**: ユーザーが操作を試みた時にエラーダイアログを表示（reactive）
- **B**: 起動時 / リフレッシュ時に前提条件をチェックし、事前に警告 + 操作を無効化（preflight）
- **C**: A と B の組み合わせ（preflight しつつ、それでも失敗したらエラー表示）

## 決定

**B を基本方針とする。preflight が困難または重すぎる場合のみ A にフォールバックする**

## 理由

- 「ボタンを押す」というユーザーの能動的な行動に対して即座に「できません」と返すのは、期待を裏切る体験になる
- 事前に警告とボタン無効化を組み合わせることで、ユーザーは「今この操作はできない理由」を理解した状態で UI を操作できる
- バナー警告は「解決方法のガイド」を含められるため、ユーザーが自己解決しやすい
- 開発者本人がこの UX を強く好んでいる

## Grove 全体への適用ガイドライン

以下のようなケースに本原則を適用する:

### 起動時に検出すべき前提条件
- `code` コマンドの存在（VS Code 起動機能の前提）
- `git` コマンドの存在
- 将来追加するエディタ連携（Cursor 等）の前提コマンドの存在
- 将来の Claude Code 連携で必要となる前提（claude バイナリの存在等）

### リフレッシュ時に検出すべき状態
- 登録済みリポジトリのパスが存在しない（削除された等）
- worktree のディレクトリが存在しない（外で削除された）
- `.git/worktrees/` 配下の参照が壊れている

### UI への反映方針
- **アプリ上部のバナー警告**: アプリ全体に影響する問題（前提コマンド不在等）
- **カード上の警告マーク**: 特定の worktree に紐づく問題（パス消失、参照破損等）
- **ボタンの disabled 化**: 該当機能が実行不可能な場合は対応するボタンを無効化
- **ツールチップ**: 無効化されたボタンにホバーした時、理由を簡潔に説明

## 例外（A を採用してよいケース）

以下のケースでは preflight が困難または非効率なため、エラー表示で対応してよい:

- 実行時にしか判定できない条件（ネットワークエラー、競合状態等）
- preflight チェックのコストが高すぎる（毎回のリフレッシュで全 worktree の `git fetch` を走らせる等）
- 前提条件が頻繁に変わる（外部プロセスの状態等）

## 却下した選択肢の理由

- **A（reactive のみ）**: 開発者本人が明確に嫌う UX。ユーザーの能動的行動を裏切る
- **C（A と B の組み合わせ）**: B を徹底すべきで、A はあくまで例外時のフォールバックとして位置付けるべき。「組み合わせ」と書くと A が常用される懸念がある
