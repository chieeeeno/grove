# ADR-0014: 自動コードレビュースキル (review-pr-loop) の運用方針

**日付**: 2026-04-16（初版） / 2026-04-17（論点 I / J / K を追加）
**ステータス**: 確定

## 背景

Grove の品質担保は手動の `/simplify` 実行に依存しており、レビュー観点の抜け漏れと「指摘 → 修正 → 再レビュー」往復の属人化という課題がある。2026-04-12 のセッションでは `/simplify` を 3 回回し 27 件の指摘を 11 コミットで処理したが、この運用を人間の集中力と記憶に頼るのは継続性に乏しい。

PR URL を渡すだけで自己ループでレビュー・修正・再レビューを回す Claude Code スキル `review-pr-loop` を整備する（Issue #55）。スキルの振る舞いには複数の設計トレードオフがあり、本 ADR で方針を固定する。

## 検討した論点と決定

### A. 自動 push を許容する範囲

- **push-A**: push まで自動化（ドラフト PR 限定）
- **push-B**: commit まで自動、push は人間 ✅ 採用
- **push-C**: commit もせず diff 提示のみ
- **push-D**: フラグ切替

**決定: push-B（commit のみ自動、push は人間）**

### B. レビュー実装方式

- **impl-A**: 既存 `/simplify` を内部呼び出しのみ
- **impl-B**: 独自プロンプトで PR レビュー専用ロジック
- **impl-C**: ハイブリッド（`/simplify` + Grove 独自観点を上乗せ） ✅ 採用

**決定: impl-C（ハイブリッド）**

### C. 終了条件の定義

- **end-A**: 指摘件数ベース（残 < N 件で終了）
- **end-B**: 重大度ベース（critical/major = 0 で終了） ✅ 採用
- **end-C**: 最大ループ回数のみで制御
- **end-D**: LLM 自己評価スコア

**決定: end-B（重大度ベース — critical/major = 0 で終了）**。minor は残ってよい。

### D. 最大ループ回数

- **loop-A**: 3 回
- **loop-B**: 5 回 ✅ 採用
- **loop-C**: 10 回

**決定: loop-B（5 回）**

### E. minor 指摘の見送り判断

- **minor-A**: ループ中にその都度ユーザー確認
- **minor-B**: ループ中は pending バッファに蓄積、全レビュー終了後に一括でユーザー確認（全対応 / 個別選択 / 全見送）
- **minor-C**: ユーザー確認を挟まず自動判断
- **minor-D**: ループ中は pending バッファに蓄積、post-review でユーザー確認はせず全件見送り扱いにして、最終 LGTM（または総評）コメント内に要約リストとして記載 ✅ 採用（2026-04-17 改訂）

**決定: minor-D（post-review では個別ユーザー確認を省略し、LGTM 内にサマリーとして記録）**

初版（2026-04-16）では minor-B（post-review での一括ユーザー確認）を採用していたが、
実運用 dogfooding を通じて「ユーザー確認のインタラクションを毎回挟むよりも、
最終 LGTM 内に要約としてまとめた方が履歴が追いやすい」と判断し minor-D に改訂。
対応要否は将来の PR / issue で別途判断する運用にする。

### F. PR コメントの形式

- **comment-A**: PR 全体コメントのみ
- **comment-B**: 行コメント + PR 全体総評（混合） ✅ 採用
- **comment-C**: サマリーのみ（行コメントは将来拡張）

**決定: comment-B（混合）**。critical/major は行コメント、総評は PR 全体コメント。

### G. 見送り理由の記録と再評価

- **skip-A**: 見送り項目は記録しない（自動修正したものだけコメント）
- **skip-B**: 見送り内容 + 理由 + ループ番号をコメントとして記録し、次ループで見送り判断の妥当性自体を再レビュー対象にする ✅ 採用

**決定: skip-B**

### H. 対応完了コメントの扱い

- **resolve-A**: 何もしない（コメントが蓄積する）
- **resolve-B**: GitHub GraphQL `minimizeComment(classifier: RESOLVED)` で非表示化 ✅ 採用

**決定: resolve-B**

### I. 各ラウンドのレビュー結果の記録方式

- **record-A**: 何も記録しない（総評コメントのみ）
- **record-B**: 全ラウンドの詳細を GitHub PR コメントとして投稿（PR が重くなる）
- **record-C**: 各ラウンドの詳細は `docs/review-result/` にローカル保存（`.gitignore` 対象）し、PR にはラウンドサマリー（要約）のみ投稿 ✅ 採用

**決定: record-C**

ファイル名規約:
`docs/review-result/code-review-pr<PR番号>-<SESSION_TS>-round<N>.md`

- `SESSION_TS` はスキル起動時に `date +%Y%m%d-%H%M%S` で取得（秒単位で一意）
- 同一 PR に対して別時刻に再起動した場合、`SESSION_TS` が異なるため命名衝突しない

### J. ラウンドサマリーコメントの扱い

- **round-summary-A**: 投稿しない（総評のみ）
- **round-summary-B**: 各ラウンド終了時に投稿し、古いラウンドのサマリーは `minimizeComment(classifier: OUTDATED)` で非表示化（削除せず、トグル展開で閲覧可能） ✅ 採用

**決定: round-summary-B**

「どういう指摘が入ったか」を GitHub 上に履歴として残す目的。minimize（削除では
なく折りたたみ）にすることで、最新ラウンド情報が目立ち、かつ履歴は追える。

### K. LGTM コメントと強制停止時の扱い

- **lgtm-A**: LGTM を明示的に出さず、総評のみで終える
- **lgtm-B**: 品質基準クリア時に LGTM コメントを追加で投稿 ✅ 採用

**決定: lgtm-B**

投稿条件:
- `critical + major == 0` **かつ** 最大ループに到達していない（= 正常終了）

最大ループ到達時（`round >= max_loop` で強制停止）は LGTM を投稿しない。
総評コメント（kind=summary）に「⚠️ 最大ループ到達で強制停止、レビュー
未完了、人間レビュワーにハンドオフ」を明記する。

## 理由

### push-B（commit のみ自動、push は人間）を採用した理由

- push した瞬間 CI が走り、チームに可視化される副作用が大きい。人間の最終確認を必ず挟みたい
- Grove の lefthook pre-commit フックで oxlint / prettier / clippy / vitest が並列実行されるため、commit 時点で最低限の品質は担保される
- push-A（自動 push）は運用リスクが大きく、ドラフト PR 限定でも事故の可能性がある
- push-C（diff のみ）は既存 `/simplify` と差別化できず、スキル化の価値が薄い
- push-D（フラグ切替）は選択肢を増やすだけで初期運用には不要

### impl-C（ハイブリッド）を採用した理由

- `/simplify` はすでに運用実績があり、一般的な品質観点で頼れる
- Grove 固有の観点（CLAUDE.md テスト必須、Doc コメント必須、Rust デスクトップアプリ特有の panic / メモリリーク / unsafe / リソース解放、ADR 整合）は `/simplify` では拾えない
- ユーザー指定で「Rust 部分はクラッシュ危険性・メモリリーク等のデスクトップアプリで最低限担保すべき項目をテスト項目として入れてほしい」との明確な要求あり
- impl-A だと Grove 固有観点が抜け、impl-B だと `/simplify` の蓄積を捨てることになる

### end-B（重大度ベース）を採用した理由

- 「件数 < N」だと軽微な指摘ばかり残る場合にループが続いて非効率
- critical/major は放置できない指摘、minor は「直った方が良いが blocker ではない」指摘という運用が直感的
- LLM 自己評価スコア（end-D）は主観的で閾値の根拠を説明しにくい
- 重大度分類はレビューの粒度を言語化する強制力にもなる

### loop-B（5 回）を採用した理由

- 3 回だと複雑な PR で収束しきらない懸念
- 10 回はトークン消費が大きく、5 回で収束しない PR は人間の判断が必要なケースが多い
- バランス型の 5 回で、収束しなければ人間にハンドオフする方針

### minor-D（post-review で LGTM 内にサマリー記載、個別ユーザー確認は省略）を採用した理由（2026-04-17 改訂）

初版では minor-B（post-review での「全対応 / 個別選択 / 全見送」ユーザー確認）を
採用していたが、PR #58 での dogfooding を通じて以下の課題が見えた:

- 毎回 AskUserQuestion でユーザーの判断を仰ぐと、スキル自動化の価値が薄れる
- minor はそもそも「直った方がいいが blocker ではない」指摘であり、個別判断の
  コストに見合わないケースが多い
- 個別の `kind=skipped` 行コメントを minor ごとに投稿すると、PR コメント欄が
  ノイズで埋まる（critical/major 対応コメントが見えにくくなる）

改訂後の minor-D では:

- minor は pending バッファに蓄積するまでは変わらない
- post-review では「全件見送り扱い」にして個別 AskUserQuestion を挟まない
- 最終 LGTM（または強制停止時は総評）コメント内に「🤔 見送った minor 指摘」
  セクションを設け、全件の要約リスト（指摘内容 + 対象 + 見送り理由）を記載
- 「どんな指摘が出て、なぜ見送ったか」は 1 コメントで俯瞰できる
- 将来の対応要否は別 PR / issue で人間が判断する（スキルの責務外）

### skip-B（見送りの記録 + 次ループ再評価）を採用した理由

- 見送り判断自体が誤っている可能性がある（最初のループで「設計判断が必要」と判断したが、後続の修正で状況が変わっているケース等）
- 見送り理由を明文化してコメントに残すことで、レビューの透明性が上がる
- 次ループで「この見送り判断は今も妥当か」を再評価すれば、初手の判断ミスを拾える
- コメントが PR に残ることで、人間レビュワーも判断経緯を追える

### resolve-B（minimize で非表示化）を採用した理由

- ループが進むと指摘コメントが蓄積して PR が読みにくくなる
- 修正済みコメントを minimize すれば、未解決コメントだけが目立つ
- 誤爆防止のため、スキル由来コメントを識別するマーカー `<!-- review-pr-loop:round=N;kind=... -->` を必ず本文に含め、minimize 対象はマーカー付きコメントに限定する
- 他者（Copilot や人間レビュワー）のコメントは minimize しない

### record-C（ローカル保存 + GitHub 要約）を採用した理由

- 各ラウンドの詳細指摘（数十件 × 5 ラウンドで最大数百件）をすべて GitHub コメントに投稿すると PR が重くなり、レビューの可読性が落ちる
- 一方で「どんな指摘が出たか」は履歴として残したい（リグレッション防止・運用知見の蓄積）
- 詳細はローカル（`docs/review-result/`）、要約は GitHub という分離で両立する
- 詳細はスキル実行者のローカルマシンに残るので、後から特定の指摘を調べたい時に参照できる
- `.gitignore` 対象にすることで誤ってリポジトリに含めない（レビュー詳細は commit すべきアーティファクトではない）

### round-summary-B（ラウンド毎の要約投稿 + minimize）を採用した理由

- 「各ラウンドで何が指摘されたか」を GitHub 上にトレーサビリティとして残す
- 5 ラウンド分のサマリーが累積すると PR が縦長になるため、古いラウンド分は `minimizeComment(OUTDATED)` で折りたたむ
- OUTDATED を選ぶのは「内容が古くなった」というニュアンスが適切（RESOLVED は解決済みを示すが、ラウンドサマリーは「古い断面」であって解決済みではない）
- minimize は削除ではないため、GitHub UI 上でトグルクリックすれば全履歴が閲覧可能
- これにより「最新状況に集中しつつ、履歴も辿れる」状態を作る

### lgtm-B（LGTM コメント追加 + 強制停止時は未投稿）を採用した理由

- 品質基準をクリアしたことを PR 上で明示的に宣言する
- 「`kind=summary`（詳細総評）」と「`kind=lgtm`（宣言のみ）」を分けることで、後者は人間レビュワーが視覚的に見つけやすくなる（PR 画面で LGTM コメントを探すのが楽）
- 強制停止（最大ループ到達）時に LGTM を出すと「品質基準クリア」との誤解を招くため、明示的に出さない
- 強制停止時は総評に「⚠️ 強制停止・レビュー未完了」を明記することで、人間レビュワーに引き取りを促す

## 安全装置

本 ADR で固定する安全装置:

1. **main / master / detached HEAD への直接 commit 禁止**: `git rev-parse --abbrev-ref HEAD` で検証し、値が `main` / `master` / `HEAD` なら commit せず停止（detached HEAD 時の戻り値は `HEAD`）
2. **force push 禁止**: そもそも push しない設計なので該当しない
3. **無限ループ抑止**: 最大 5 ループに到達したら必ず停止
4. **同一箇所の繰り返し書き換え検出**: 同一ファイル × 同一行範囲を 2 ループ連続で書き換えたら停止
5. **見送り再評価のループ間追跡**: 同じ指摘を 2 ループ連続で「見送り」と判断したら 3 ループ目以降は再評価スキップ（総評に明記）
6. **コメント誤爆防止**: `<!-- review-pr-loop:round=N;kind=... -->` マーカー付きコメントのみ minimize 対象

## コメントのライフサイクル

| フェーズ | 種類 | kind | 絵文字 | 投稿タイミング / 扱い |
| --- | --- | --- | --- | --- |
| ループ中 | 見送り（critical/major） | `skipped` | 🤔 | 見送り確定時に投稿 |
| ループ中 | 解消済み指摘 | — | — | 次ラウンド開始時に `minimizeComment(RESOLVED)` で非表示化 |
| ラウンド終了 | ラウンドサマリー | `round-summary` | 🔁 | 各ラウンド終了時に投稿。次ラウンド開始時に前ラウンド分を `minimizeComment(OUTDATED)` で折りたたみ（削除せず、トグル展開で閲覧可能） |
| post-review | 見送り（minor） | — | 🤔 | **個別コメントとしては投稿しない**。最終 LGTM（または強制停止時は総評）コメント内の「🤔 見送った minor 指摘」セクションに全件の要約リストとして集約記載 |
| post-review | 残件行コメント | `remaining` | 🔴🟠🟡 | 終了時に投稿 |
| post-review | 総評 | `summary` | 🤖 ✨ 🛠️ 🤔 📝 📊 | 終了時に投稿。強制停止時は「⚠️ レビュー未完了」を明記 |
| post-review | LGTM | `lgtm` | ✅ | 正常終了（critical/major=0 かつ最大ループ未到達）のときのみ投稿 |

## レビュー結果のローカル記録

各ラウンド終了時、詳細な指摘内容と判断根拠を `docs/review-result/` に
マークダウンで保存する（`.gitignore` 対象）:

```
docs/review-result/code-review-pr<PR番号>-<SESSION_TS>-round<N>.md
```

- `SESSION_TS`: スキル起動時に `date +%Y%m%d-%H%M%S` で取得したタイムスタンプ
- 同一 PR に対する再起動時は `SESSION_TS` が変わるため命名衝突しない
- ファイル内容は GitHub に投稿するラウンドサマリーの一次ソース

## 運用上の注意

- **適用対象**: 本スキルを M0 実装コード（Tauri/React 本体）に対して回し始めるのは M1 以降。M0 進行中は手動 `/simplify` を継続する。ただし本スキル自身の整備 PR（Issue #55）や M1 以降のインフラ系 PR に対しては M0 期間中でも使用可能
- M1 で M0 コードベースにも本スキルを本格導入し、dogfooding を重ねて運用上の課題を洗い出す
- 運用中に課題が見つかれば、本 ADR を更新もしくは追補 ADR を起票する
