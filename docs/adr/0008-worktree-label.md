# ADR-0008: worktree ラベルの仕様と永続化キー

**日付**: 2026-04-07
**ステータス**: 確定

## 背景

Grove の worktree カードには「今この worktree で何の作業をしているか」を表すラベルを表示する。
ユーザーは worktree のディレクトリ名を「作業内容のラベル」として使う運用をしているが、UI 上ではディレクトリ名とは別に編集可能なラベルを持たせたい。

このラベルを Grove の永続化ストアに保存する際の「キー」を何にするかが論点。
ラベルの紐付けが壊れると、ユーザーが付けた情報が失われるため、設計上の重要決定となる。

## 検討した選択肢

### ラベルのデフォルト値
- **default-A**: ブランチ名（例: `feature/add-detail-panel`）
- **default-B**: worktree のディレクトリ名（例: `add-detail-panel`）
- **default-C**: 空欄

### ラベルの永続化キー
- **key-A**: worktree の絶対パス
- **key-B**: ブランチ名 + リポジトリID
- **key-C**: Grove が発行する内部 UUID
- **key-D**: パス優先 + ブランチ名フォールバックの複合キー

### ディレクトリ rename 時のラベルハンドリング
- **rename-A**: 何もしない（ラベルは消える）
- **rename-B**: 自動検知して store のキーを更新
- **rename-C**: パス + ブランチ名の複合キーで吸収
- **rename-D**: 「孤児ラベル」として残し、ユーザーに紐付けを提案
- **rename-E**: Grove 内から rename 機能を提供し、その時に store も同時更新

## 決定

- **デフォルト値**: `default-B`（worktree のディレクトリ名）
- **永続化キー**: `key-A`（worktree の絶対パス）
- **rename ハンドリング**: `rename-A`（何もしない、ラベルは消える）
- **rename 機能**: M0 では実装しない。**M1 以降の早期に追加する**

## 理由

### なぜディレクトリ名をデフォルトにしたか
- ユーザーは `git worktree add` 実行時の dir 名を「作業内容のラベル」として使う運用をしている
- ブランチ名は技術的命名規約（feature/xxx 等）に縛られがちで、人間の認知に馴染みにくい
- dir 名は自由度が高く、開発者が「何の作業をしているか」を直感的に表現する場として既に使われている
- これは Grove 全体の設計思想（Git の都合より開発者の認知に寄り添う）にも合致する

### なぜ絶対パスをキーにしたか
- ユーザーが「dir 名は基本変えない」と明言しており、絶対パスは実質的に不変
- 一意性が確実で、実装が最もシンプル
- 複合キーや UUID 方式は、稀なケースのために複雑度を上げるオーバーエンジニアリング

### なぜ rename 時に何もしないか
- ユーザーの運用上 rename は例外ケース
- 例外ケースのために自動検知ロジック（rename-B/C/D）を入れるのは過剰
- 「Grove 内から rename したら store も更新、外から触ったら自己責任」という線引きが分かりやすい

### なぜ rename 機能は M0 に入れず、M1 以降で追加するか
- 開発者本人としては rename 機能は欲しい
- しかし M0 段階では「自分が grove-app の worktree を Grove で管理できる」が最優先で、リネーム機能なしでもこのゴールは達成可能
- 滅多に使わない機能で M0 完成を遅らせたくない
- ただし M1 以降の早い段階で対応する意志がある

## 却下した選択肢の理由

- **default-A（ブランチ名）**: ブランチ名は Git の都合で命名されがちで、ユーザーの「作業ラベル」としての使い方に合わない
- **default-C（空欄）**: 初期表示が無情報になり、worktree が増えた時の認知負荷が高い
- **key-B（ブランチ名 + リポジトリID）**: 同名ブランチの別 worktree が衝突するリスク。実装も複雑
- **key-C（UUID）**: Grove 外で作成された worktree との紐付け管理が複雑になる
- **key-D（複合キー）**: ロジックが複雑で、誤マッチのリスクがある
- **rename-B/C/D**: 例外ケース対応のためのオーバーエンジニアリング
- **rename-E（M0 で rename 機能込み）**: 滅多に使わない機能のために M0 完成を遅らせるべきでない

## 将来の対応予定（M1 早期）

以下を M1 段階で追加する:

1. **Grove 内からの rename 機能**
   - カードのメニューに「Rename worktree」項目を追加
   - 裏で `git worktree move <旧パス> <新パス>` を実行
   - store 内のラベルキー（旧パス → 新パス）を同時更新
   - ラベルはそのまま引き継ぐ

2. **rename 時の整合性保証**
   - Grove 内 rename: 完全に追従
   - 外部 rename（ターミナル等）: 引き続きラベル消失（仕様）

この対応の優先度は M1 内で高く設定する。
