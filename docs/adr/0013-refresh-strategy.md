# ADR-0013: リフレッシュ戦略は M0 ではポーリング、M1 早期にファイル監視へ進化

**日付**: 2026-04-07
**ステータス**: 確定

## 背景

Grove は外部（ターミナル、Claude Code スキル等）で発生した worktree の変化（新規作成、ファイル変更、コミット等）を検知して UI に反映する必要がある。
ユーザーは Claude Code スキルで Grove の外から worktree を作成する運用をしているため、自動リフレッシュは必須機能となる。

更新方式には複数の選択肢があり、実装コストとリアルタイム性のトレードオフがある。

## 検討した選択肢

### 自動リフレッシュの要否
- **need-A**: 自動リフレッシュ必須
- **need-B**: 手動リフレッシュボタンだけで十分
- **need-C**: 両方提供

### リフレッシュ方式
- **method-A**: 時間間隔ポーリング（例: 5 秒ごとに `git status`）
- **method-B**: ファイル監視（`notify` crate で `.git/` 等の変化を検知）
- **method-C**: ハイブリッド（ファイル監視 + 念のためのポーリング）

### 手動リフレッシュボタン
- **manual-A**: 置く
- **manual-B**: 置かない

## 決定

- **need-C**: 自動リフレッシュ + 手動ボタンの両方を提供
- **method-A** で M0 を実装（時間間隔ポーリング）
- **manual-A**: 手動リフレッシュボタンを置く（Cmd+R ショートカットも M0 で提供）
- **M1 早期に method-B（ファイル監視）への移行を実施する**（優先度: 高）

## 理由

### なぜ自動リフレッシュが必須か
- ユーザーは Claude Code スキルで Grove の外から worktree を作成する運用
- 手動リフレッシュのみだと「外で worktree 作るたびに Grove に戻ってボタンを押す」必要があり、ストレスが高い
- ユーザー本人が「手動リフレッシュ押す方がストレス」と明言

### なぜ M0 はポーリングか
- 実装が最もシンプルで、M0 完成までの時間を最小化できる
- ポーリング間隔は後から調整可能（5 秒が重ければ 10 秒に伸ばせる）
- ユーザーも「5 秒待てる」と許容を表明
- 動くものを早く作ってボトルネックが出てから最適化する方針

### なぜ M1 早期にファイル監視へ移行するか
- ユーザーが「ファイル監視で反応する機能は欲しい、優先度は高め」と明言
- ポーリング方式は worktree 数が増えると線形にコストが増える（10 個 × 5 秒ごとに `git status`）
- ファイル監視ならほぼリアルタイム反映でき、CPU 負荷も低い
- M0 で動かしながらドッグフーディングする中で「待たされる感」が顕在化する想定

### なぜ手動ボタン + Cmd+R ショートカットを置くか
- ユーザー本人が「せっかち」と表明し、即時更新したい場面がある
- 自動リフレッシュが何らかの理由で詰まった時の救済策になる
- 設置コストが極めて低い（アイコン 1 個 + ショートカット登録 1 行）
- Cmd+R は macOS のリロード操作として広く認知されているため学習コストゼロ

## 却下した選択肢の理由

- **need-B（手動のみ）**: 上記の通り、ユーザーの実運用に合わない
- **method-B（最初からファイル監視）**: 実装複雑度が高く、`notify` crate の学習コスト + 監視対象パスの管理 + macOS FSEvents の罠（深階層で重い等）対応が必要。M0 の完成スピードを優先
- **method-C（最初からハイブリッド）**: さらに複雑度が上がる。M1 でファイル監視に移行する際にハイブリッドにするかは別途判断
- **manual-B（手動ボタンなし）**: せっかちユーザーの体験を損なう、自動失敗時の救済策がなくなる

## M1 移行時の検討事項

ファイル監視に移行する際は以下を考慮する:

1. **監視対象パス**
   - 各 worktree の `.git/index`、`.git/HEAD`、ワーキングディレクトリのファイル
   - 親リポジトリの `.git/worktrees/` ディレクトリ（worktree の追加 / 削除を検知）

2. **イベントのデバウンス**
   - ファイル変更が短時間に大量発生した場合、`git status` を都度叩くと無駄
   - 100ms 〜 500ms 程度のデバウンスを入れる

3. **監視解除**
   - リポジトリ削除 / worktree 削除時に確実にウォッチャーを解除する
   - リソースリーク防止

4. **macOS FSEvents の挙動**
   - 深いディレクトリ階層を再帰監視すると重い場合がある
   - `node_modules/` などの巨大ディレクトリを除外する設計が必要

5. **フォールバック**
   - ファイル監視がエラーで停止した場合、ポーリングに自動フォールバックする設計を検討
   - もしくは ADR を更新して method-C（ハイブリッド）に移行する

## ポーリング間隔の初期値

M0 段階のポーリング間隔は **5 秒** を初期値とする。
ドッグフーディング中に「重い」「待たされる」と感じたら 10 秒や 3 秒に調整する。最終的な値は M1 移行のタイミングで実測値ベースで決定する。
