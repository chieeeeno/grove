# ADR-0006: テレメトリは M0 / M1 では実装しない（将来 opt-in で追加余地あり）

**日付**: 2026-04-07
**ステータス**: 確定

## 背景

アプリの利用状況（起動回数、使用機能、エラー発生状況等）を匿名収集するテレメトリ機能を入れるかどうかの判断。開発者ツール界隈ではプライバシーへの感度が高く、一度入れた機能を後から抜くのは難しいため、初期の方針を明確にしておく必要がある。

## 検討した選択肢

- **A**: テレメトリを実装しない
- **B**: opt-in（デフォルト OFF、ユーザーが明示的に有効化）
- **C**: opt-out（デフォルト ON、嫌なユーザーが無効化）

## 決定

**A: M0 / M1 ではテレメトリを実装しない**

ただし将来（M2 以降）必要性が出た場合、**opt-in 形式（B）でのみ追加を検討する**。opt-out（C）は採用しない。

## 理由

### 今 A を選ぶ理由
- M0 / M1 は自分用 + 知人配布段階で、フィードバックは直接もらえる
- テレメトリ実装には付随コストが多い（送信先サーバー、エンドポイント、データスキーマ設計、プライバシーポリシー文書化など）
- 限られた個人開発のリソースは「機能を作る」に全振りした方がよい
- 一度実装したテレメトリを後から抜くのは難しいが、実装しない決定は後からいつでも覆せる

### 将来追加するなら opt-in 限定にする理由
- 開発者ツールにおいて opt-out テレメトリは強く嫌われる文化がある（VS Code、JetBrains が批判される事例多数）
- ユーザーの信頼を損ねるリスクが、得られるデータの価値を上回る
- opt-in でも「使ってくれている熱量の高いユーザー」のデータは取れるため、改善に十分活用できる

## 却下した選択肢の理由

- **C（opt-out）**: 開発者向けツールでデフォルト ON のテレメトリは信頼を損ねる。Grove のターゲット層は特にプライバシー感度が高い

## 将来の追加条件（参考）

以下が満たされた場合、ADR を更新して opt-in テレメトリの追加を検討する:

- M2 以降で公開ユーザー数が増え、フィードバックの直接収集が困難になった
- 改善判断のために定量データが必要になった
- プライバシーポリシーを文書化できる体制ができた
- データを送信・保管するインフラを用意できる
