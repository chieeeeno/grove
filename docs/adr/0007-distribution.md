# ADR-0007: M1 配布形態を GitHub Releases のみ・署名なしとする

**日付**: 2026-04-07
**ステータス**: 確定

## 背景

M1（β 配布）の段階で、Grove をどこからどう配るかを決める必要がある。配布チャネルとコード署名の有無は別軸で判断できるため、両方を検討する。

macOS アプリは配布時に「コード署名 + 公証（notarization）」を行わないと、ユーザー起動時に「開発元が確認できません」の警告が出る。署名には Apple Developer Program の登録（年 $99）が必要。

## 検討した選択肢

### 配布チャネル
- **A**: GitHub Releases のみ（dmg/zip を直接ダウンロード）
- **B**: GitHub Releases + 自作 Homebrew tap（Cask 形式、`brew install --cask` で導入可能）
- **C**: 公式 Homebrew core（審査必要、メンテ義務あり）

### コード署名
- **S0**: 署名なし（ユーザーは初回のみ「右クリック→開く」が必要）
- **S1**: Apple Developer Program 登録 + 署名・公証（年 $99）

## 決定

**A + S0: GitHub Releases のみ・署名なしで M1 配布する**

署名（S1）は M1 → M2 移行のタイミングで再判断する。Homebrew tap（B）は M1.5 以降で必要性が出たら追加する。

## 理由

### 配布チャネルを A にした理由
- M1 は知人配布フェーズで、Tauri が標準で生成する dmg を GitHub Releases に置くだけで十分機能する
- Homebrew tap（B）は無料だが、tap 用リポジトリの管理・Cask 定義（Ruby）の保守・リリースごとの SHA256 更新といった付随作業が発生し、M1 段階では恩恵に対して手間が大きい
- B は M1.5 や M2 で「もっとラクに配りたい」と感じたタイミングで後から追加可能
- 公式 Homebrew core（C）は審査と継続メンテが必要で、M2 以降の検討事項

### 署名を S0 にした理由
- M0 / M1 段階で年 $99 のサブスクリプションをコミットするのは、プロジェクトの継続意志がまだ固まっていない時期にはリスクが大きい
- 「途中で払うのをやめると新規リリースが詰まる」性質があるため、`Grove を続ける覚悟ができた瞬間 = サブスクを開始するタイミング` を一致させる方が合理的
- 知人配布フェーズなら「初回のみ右クリック→開く」を README に書くことで通じる
- 自分の Mac での開発中は Gatekeeper が一度許可を覚えるため、開発中のストレスは限定的
- 過去にリリースした dmg は将来証明書が失効しても影響を受けない（公証は1回通せば永続有効）ため、後から S1 に切り替えてもユーザー体験に断絶が生じない

## 却下した選択肢の理由

- **B（Homebrew tap）**: 無料だが M1 段階では手間が恩恵を上回る。M1.5 以降の追加候補
- **C（公式 Homebrew core）**: 審査・メンテ義務があり、M2 以降の検討事項
- **S1（最初から署名）**: M0 / M1 段階で年 $99 をコミットするのは継続意志が固まる前のリスク。完成して使い始めることを最優先する

## トレードオフの自覚

- 配布した dmg は起動時に警告が出る。ユーザーには「開発元が確認できません」のダイアログを毎回または初回に見せることになる
- 開発者本人はこの警告を「個人的に好きではない」と認識しており、解消したい意志は持っている
- そのため M1 → M2 移行時に S1 への切り替えを必ず再検討する

## 将来 S1（署名）に切り替える条件

以下が満たされたタイミングで ADR を更新し、S1 への切り替えを判断する:

- M1 が完成し、不特定多数への公開（M2）を本気で目指す段階に入った
- Grove を継続的に育てる意志が固まっている（年 $99 を継続して払う判断ができる）
- 既存ユーザー（知人配布層）から「警告が気になる」というフィードバックが出た

## 補足: 後から署名に切り替える際の作業概要

将来 S1 に切り替える場合、必要な作業は以下のみ。コード本体への変更は不要:

1. Apple Developer Program に登録（$99/年）
2. 開発者証明書を取得し Keychain に登録
3. `tauri.conf.json` に署名情報を追記
4. ビルドコマンドに環境変数を渡す
5. 公証（notarization）コマンドをリリースフローに組み込む

既存ユーザーへの影響もない（次のアップデートから警告が消えるだけ）。
