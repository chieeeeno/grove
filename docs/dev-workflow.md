## 開発の基本スタンス

**「自分でコードを書かず、AI との会話で開発を進める」**

設計・デザイン・実装のすべてにおいて、Claude（Claude Code）を対話相手として活用し、
自分はディレクターとして「何を作るか」「なぜそう決めるか」の意思決定に集中する。

## フェーズごとのワークフロー

### Phase 0: 設計フェーズ

**期間**: 実装着手前  
**ツール**: Claude（対話）+ Markdown ドキュメント

#### やったこと

1. **設計書（grove-design.md）の策定**
   - アプリの目的・ターゲット・機能要件・データモデル・API 設計を文書化
   - 処理フロー・シーケンス図（§11）を追加

2. **ADR（Architectural Decision Records）の策定**
   - 意思決定ごとに独立した ADR ファイルを作成（計 13 件）
   - フォーマット: 背景 / 検討した選択肢 / 決定 / 理由 / 却下した選択肢の理由
   - アプリ名 / 対象 OS / ライセンス / UX 原則 / リフレッシュ戦略など幅広い決定を記録

3. **ROADMAP.md の策定**
   - M0（自分用 α）/ M1（β 配布）/ M2（正式リリース）のマイルストーン定義
   - 各フェーズのスコープと完成条件を明文化

4. **スパイク調査（Phase 2 の実現可能性検証）**
   - 将来機能（Claude Code エージェント連携）が技術的に実現可能かを先に検証
   - 三次調査まで実施し、公式ドキュメントで裏付けを確認してから設計を確定

#### ポイント

- **実装より先に ADR を書く**: 実装中に「なぜこう決めたか」で迷わないようにする
- **却下理由も必ず書く**: 将来「やっぱりこっちにしよう」とならないように、なぜ却下したかを残す
- **不確実性の高い部分を先に潰す**: スパイク調査で「やってみたら無理だった」を防ぐ

### Phase 1: UI デザインフェーズ

**期間**: 設計フェーズ完了後  
**ツール**: Claude + Pencil（MCP サーバー経由）

#### やったこと

1. **デザイン変数の定義**
   - カラー・スペーシング・角丸などをトークンとして定義
   - ダーク / ライト両テーマ対応

2. **画面モックの作成**（`docs/design/grove-ui.pen`）
   - メイン画面（3カラムレイアウト、worktree カード 3 種）
   - 設定ダイアログ
   - ホバー & アクティブ状態
   - 削除確認ダイアログ
   - ラベル編集の状態遷移
   - preflight 警告バナー
   - 全画面をダーク / ライト両テーマで作成

#### 進め方

- Claude に自然言語でデザイン指示を出す（例: 「3カラムレイアウトのメイン画面を作って、サイドバー 220px、カードは 2 列 Grid で」）
- Pencil MCP サーバーが Claude の指示を受けてデザインファイルを操作
- スクリーンショットで確認しながらイテレーション
- 自分でデザインツールを操作することはゼロ

#### ポイント

- **デザインの意図を言語で正確に伝えるスキルが重要**
- Figma と違ってインタラクティブプロトタイプは作れないが、静的モックとして十分
- 生成されたモックをそのまま実装の参照として使える（工程の連続性）

### Phase 2: 実装フェーズ（進行中）

**期間**: 2026-04 〜

## 意思決定の原則

開発を通じて一貫して守っている判断軸。

1. **M0 完成を最優先**: 滅多に使わない機能のために完成を遅らせない
2. **オーバーエンジニアリングしない**: 例外ケースのために複雑度を上げない
3. **事前警告 UX**: 事後エラーより、事前バナー + ボタン無効化（ADR-0012）
4. **Enter 単独で確定しない**: 入力 UI の確定は確定ボタン or Cmd+Enter（ADR-0008）
5. **コミットは論理単位で分割**: まとめて 1 コミットにしない
6. **不確実性を先に潰す**: 将来機能はスパイク調査で実現可能性を確認してから設計する

## 振り返り・気づき（随時追記）

- 個人開発でも ADR を書くことで「設計者と実装者が同じ人間でも」判断のブレが減る
- AI に「何をどう作るか」を任せることで、自分は「何を作るべきか」に集中できる
- デザインを言語で指示するには、元々の設計書が詳細に書かれていることが重要だった
- セッションをまたいでも NEXT.md + ADR があれば文脈が復元できる
